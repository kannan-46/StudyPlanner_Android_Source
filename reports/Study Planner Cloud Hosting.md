# Host the Planner Securely and Affordably

For this app, deploy one authenticated Node.js API near the user, connect that server to MongoDB Atlas, and point the Android APK at the API’s HTTPS address. **Railway Pro is the simplest first fit if its $20 monthly subscription is acceptable**: its static outbound IP can be allowlisted in Atlas, and its service supports long-lived Socket.IO connections. Atlas Free is fine while experimenting; for a planner the owner relies on, Atlas Flex adds daily backups for **$8–$30 per 30 days**. Render offers a lower listed compute price, while Google Cloud Run can place the API in India, but both require trade-offs around Atlas network access or operational setup. Nothing in this plan provisions accounts or deploys services; the user still needs to create those and provide the resulting API URL before a cloud-connected APK can be built.

## Keep Atlas behind one authenticated API

The mobile app should send planner requests to a public API over HTTPS. The API verifies the signed-in user, reads or changes that user’s planner, and is the only component that holds `MONGODB_URI` and database credentials. Atlas should allow network access only from the API host’s outbound IP, and the API’s database user should have access only to this app’s database. MongoDB recommends least-privilege database roles and storing connection strings in environment variables or a secret manager; its Atlas IP access list supports narrow IP and CIDR rules and warns that `0.0.0.0/0` permits connections from anywhere ([Atlas network security](https://www.mongodb.com/docs/atlas/architecture/current/network-security/), [database authorization](https://www.mongodb.com/docs/atlas/architecture/current/auth/authorization/), [connection string guidance](https://www.mongodb.com/resources/products/fundamentals/atlas-connection-strings)).

That means the APK contains only the API’s public base URL, never an Atlas URI or database password. The backend code already scopes planner records to the authenticated account, so the owner can start with one account and add invited or verified accounts later without sharing planner records. Keep public registration disabled until account invitation or email verification and password recovery are ready. Hosting also does not make data live by itself: the API’s Socket.IO connection delivers change notices to active sessions, while the app fetches the current planner over the authenticated API. Reconnect and refresh after a socket or network interruption.

## Railway trades a $20 commitment for easier Atlas access

Railway is the recommended starting host for a beginner who wants the API to remain available and use live updates. It can deploy from a linked GitHub repository, provides an HTTPS domain, supports long-lived WebSockets, and offers static outbound IPv4 addresses on Pro for services such as Atlas. Pro is listed at **$20 per month**, and the subscription amount counts toward resource usage; its static address can also be shared with other Railway customers, so it is a narrow allowlist entry rather than a private network ([Railway plans](https://docs.railway.com/pricing/plans), [GitHub deployments](https://docs.railway.com/services), [static outbound IPs](https://docs.railway.com/networking/static-outbound-ips), [WebSocket limits](https://docs.railway.com/networking/public-networking/specs-and-limits)). Choose Singapore for the initial API deployment and a nearby Atlas region if Atlas offers it for the selected tier; verify the actual region and price in both account dashboards before paying.

Render is a valid lower-cost alternative: its current small paid web-service plan is listed at **$7 per month**, includes HTTPS, and supports WebSockets. Its outbound IP ranges are shared by services in the region, so the Atlas allowlist is broader than a single static address; copy the exact ranges from the created service’s dashboard and never substitute `0.0.0.0/0`. Render lists Singapore as its closest region among those researched. The free Render service sleeps after 15 minutes without traffic and can take about a minute to wake, so it is for previews rather than a responsive everyday API ([Render pricing](https://render.com/pricing), [outbound IPs](https://render.com/docs/outbound-ip-addresses), [free services](https://render.com/docs/free), [WebSockets](https://render.com/docs/websocket)).

Google Cloud Run is a credible option when an India region matters most: Google lists Mumbai and Delhi regions and usage-based pricing. Its WebSocket requests time out after at most 60 minutes, so the app must reconnect, and a fixed egress address for a narrow Atlas allowlist requires VPC routing and Cloud NAT. That adds account setup and separately billed network resources. For this beginner’s first release, that complexity outweighs the location advantage; reconsider Cloud Run if India-region hosting becomes a requirement and someone can maintain the networking setup ([Cloud Run regions and pricing](https://cloud.google.com/run/pricing), [WebSockets](https://docs.cloud.google.com/run/docs/triggering/websockets), [static outbound IP](https://docs.cloud.google.com/run/docs/configuring/static-outbound-ip), [Cloud NAT pricing](https://cloud.google.com/vpc/network-pricing)).

## Use Atlas Free for setup and Flex for safer daily use

Atlas Free (`M0`) is enough to build and check the first deployment, but it has a **512 MB storage cap**, 100 read/write operations per second, 10 GB inbound and outbound transfer per rolling week, and may pause after 30 days without connections. MongoDB’s documentation conflicts on whether a paid backup preview is available to Free accounts, so do not count on Atlas-managed Free backups; keep manual JSON exports until the account’s Atlas UI confirms otherwise ([Free limits](https://www.mongodb.com/docs/atlas/reference/free-shared-limitations/), [pause behavior](https://www.mongodb.com/docs/atlas/pause-terminate-cluster/), [backup documentation](https://www.mongodb.com/docs/atlas/backup/cloud-backup/free-cluster-backup/)).

When the owner relies on the planner, Atlas Flex is the sensible low-traffic paid tier to evaluate. It has a 5 GB cap and costs **$8–$30 per 30 days** based on use, with one daily snapshot retained for eight days; it does not provide point-in-time restore or custom snapshot schedules. That is a useful recovery window for a small app, but it is not a guarantee against losing changes made since the previous snapshot. Atlas documents its 99.995% uptime SLA for M10 and larger dedicated clusters, not for Free or Flex, so Flex should be treated as practical low-traffic hosting rather than an uptime commitment ([Flex pricing and limits](https://www.mongodb.com/docs/atlas/billing/atlas-flex-costs/), [Flex backups](https://www.mongodb.com/docs/atlas/backup/cloud-backup/flex-cluster-backup/), [production notes](https://www.mongodb.com/docs/atlas/production-notes/)).

Start with the nearest supported region that appears in Atlas cluster creation; the provider and region lists include options in Mumbai, Hyderabad, Delhi, Pune, and Chennai, but Free and Flex are not available in every region. Because the exact API host and Atlas account are not selected yet, actual latency, monthly charges, backup availability, and the matching Atlas region remain to be confirmed in the setup screens ([AWS regions](https://www.mongodb.com/docs/atlas/reference/amazon-aws/), [Google Cloud regions](https://www.mongodb.com/docs/atlas/reference/google-gcp/), [Azure regions](https://www.mongodb.com/docs/atlas/reference/microsoft-azure/)).

## Add users without changing the private data model

The current design already gives each user a separate planner document and derives ownership from the verified API session. For the first release, create one owner account privately using the server-side owner setup command. When multiple people are ready, add an invitation or verified registration and a password recovery flow, then keep every planner read, write, and live-update room scoped to the authenticated user. Do not create a separate MongoDB database account for each app user; the server uses one narrowly scoped Atlas database identity while the app’s own login determines which private planner it can access.

Keep one API instance while the Socket.IO server uses in-memory rooms. If usage later requires multiple API instances, add a shared Socket.IO adapter so a change made through one instance reaches sessions connected to another, and verify the hosting platform’s connection routing behavior. The app should continue to refresh from the API after reconnecting or returning to the foreground; a persistent socket alone is not a durability mechanism ([Socket.IO adapters](https://socket.io/docs/v4/adapter), [Redis adapter](https://socket.io/docs/v4/redis-adapter)).

## Conclusion

The first real decision is the acceptable monthly cost for always-available API hosting and managed database backups. Railway Pro with Atlas Flex is the least complicated path among the researched options for secure Atlas allowlisting plus live updates, but Render can lower the API-hosting bill if its shared outbound ranges are acceptable, and Cloud Run is worth revisiting for India-region placement. Once the accounts exist, the remaining concrete steps are to deploy the API, enter its secrets in the host, restrict Atlas access, create the owner account, and build the APK with that HTTPS URL.
